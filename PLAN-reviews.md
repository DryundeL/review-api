# План реализации: создание и редактирование обзоров

Источник требований: `SPEC-reviews.md`. План составлен по спеку и текущему коду;
код не менялся. Четыре открытых вопроса спека закрыты — см. «Принятые решения».

## Ключевая идея

Обе версии обзора живут в одной строке `reviews`, без новых таблиц:

- **Публичная версия:** существующие `title`, `rating` и новая колонка `body`.
  Лента, поиск и списки продолжают читать те же колонки.
- **Рабочая версия:** новые `draft_title`, `draft_rating`, `draft_body`
  (все допускают `NULL`) и счётчик `revision`.
- **Публикация:** копирует `draft_*` в публичные колонки и пишет
  `published_revision`. Признак «есть неопубликованные правки» —
  `revision <> published_revision`.
- **Конфликт ревизий:** автосохранение — один
  `UPDATE … WHERE id=$1 AND author_id=$2 AND revision=$3`;
  ноль затронутых строк означает 409.

## Предлагаемый API

| Маршрут | Назначение |
|---|---|
| `GET /v1/reviews/draft?mediaObjectId=` | Рабочая версия своего обзора по произведению; 404, если её нет. `no-store`. |
| `POST /v1/reviews` `{mediaObjectId, title?, rating?, body?}` | Создание при первом изменении: 201, либо 200 с уже существующим обзором без перезаписи. |
| `PUT /v1/reviews/:id/draft` `{title, rating, body, revision}` | Автосохранение: 200 с новой ревизией, 409 при конфликте, 404 для чужого обзора. |
| `POST /v1/reviews/:id/publish` `{revision}` | Публикация и «Обновить публикацию»; повтор той же ревизии возвращает 200 без событий. |
| `GET /v1/reviews/:id` | Только опубликованное, `body` вместо `blocks`. |
| `PATCH /v1/reviews/:id` | Удаляется, чтобы старый клиент не мог затереть новое содержимое. |

## Шаги на сервере

### 1. Миграции

- `00032`: добавить колонки `body`, `draft_title`, `draft_rating`, `draft_body`,
  `revision`, `published_revision`, время первой публикации и время обновления
  публикации; снять `NOT NULL` с `title` и `rating`.
- Склеить блоки по `position` в `body` и `draft_body`: `<h3>` с экранированным
  заголовком блока, затем тело. Опубликованные обзоры получают одинаковые
  рабочую и публичную версии, черновики — только рабочую.
- `review_blocks` не трогать. Худший случай по длине — 10 × (50 + 500) символов,
  в лимит 20 000 укладывается.
- В той же миграции: уникальный индекс `(author_id, media_object_id)` на все
  обзоры вместо частичного `reviews_author_media_published_uidx`. Ничего
  не удаляется; при неожиданном дубле миграция падает целиком.
- Down-миграция не удаляет новые колонки, чтобы откат не терял обзоры,
  созданные в новом редакторе.

### 2. Домен — `internal/modules/reviews/internal/domain/review.go`

- Убрать `Block`, `BlockDraft`, `parseBlocks`.
- `parseBlockBody` превратить в `parseBody`: прежний список тегов плюс `h3`,
  атрибуты по-прежнему запрещены.
- Длина считается по текстовым узлам в code points после декодирования
  сущностей; теги и границы абзацев дают 0.
- Два метода: `SaveDraft` (всё необязательно, оценка может отсутствовать)
  и `Publish` (нужны непустой текст и оценка 1–10, заголовок необязателен).

### 3. Спойлеры

Оставить `||…||` в тексте: кнопка редактора оборачивает выделение. Не нужны
атрибуты и конвертация старых данных; определение `has_spoilers` меняется
только источником (`r.body` вместо `review_blocks`).

### 4. Команды — `internal/application/command/`

- `create_review.go`: `INSERT … ON CONFLICT DO NOTHING`, затем чтение;
  существующий обзор возвращается без перезаписи.
- `update_review.go` → `save_draft.go`: сохранение рабочей версии с проверкой
  ревизии, без событий.
- Новый `publish_review.go`: одна транзакция — проверка ревизии, копирование
  в публичные колонки, outbox. `EventPublished` только при первой публикации.
- Публикация после модераторского `Unpublish` должна вернуть статус
  `published`, даже если ревизия совпадает с `published_revision`.

### 5. Порты и хранение — `ports/`, `infrastructure/write`, `infrastructure/read`

- `Replace` заменить на `SaveDraft` и `Publish`; убрать `insertBlocks`
  и `loadBlocks`.
- `spoilersExistSQL` перевести на `r.body`.
- `ListByAuthor` для своего списка: рабочие заголовок и оценка плюс
  `hasUnpublishedChanges`.
- Публичный `Get`: только `status = 'published'`, иначе 404 — в том числе автору.

### 6. HTTP — `internal/delivery/http/`

- Новые DTO: `body` вместо `blocks`, `rating` как `*int16`, причина ошибки
  в `Details` ответа 422.
- Новые обработчики и маршруты из таблицы API; удалить `PATCH /reviews/:id`.
- `middleware.BodyLimit` на маршруты записи (предложение: 256 КБ), ответ 413.
- Автор, счётчики и статус из тела запроса не принимаются.

### 7. Другие модули

- `internal/modules/feed/internal/infrastructure/read/repository.go:17`
  и `internal/modules/search/internal/infrastructure/read/repository.go`
  читают `review_blocks`; перевести на `r.body`.
- `internal/modules/gamification/internal/application/consumer/published.go`
  зависит от `blockCount`: перевести на фиксированные очки за обзор и убрать
  продвижение `blocks_written` (решение 3).

### 8. Тесты и документация

- Unit: границы 20 000 и 20 001, emoji, HTML-сущности, пустые теги, XSS,
  оценки 0/1/10/11, публикация без заголовка.
- HTTP: чужой черновик, 401, 409, 413, 422.
- Интеграционные (PostgreSQL): гонка создания, устаревшая ревизия,
  идемпотентная публикация, отсутствие повторных событий, миграция блоков.
- Обновить `docs/frontend-api-changes.md`.

## Фронтенд (отдельный репозиторий)

- Единый редактор с кнопкой «Спойлер» и общим счётчиком текста.
- Автосохранение через 1 секунду после последнего изменения, по одному запросу
  за раз; изменения во время запроса объединяются в следующий.
- Статусы «Есть несохранённые изменения», «Сохраняется», «Сохранено»,
  «Не удалось сохранить».
- Экран конфликта (409) с копированием своего текста перед загрузкой
  актуальной версии.
- Запоздалые ответы игнорируются по номеру ревизии.
- Ошибки сети, 401, 413, 422, 429 не стирают введённый текст.

## Принятые решения (2026-11-17)

1. **Контракт API.** Утверждён в виде таблицы выше.
2. **Дубли.** На проде дублей нет: уникальный индекс
   `(author_id, media_object_id)` включается сразу в миграции `00032`,
   отдельная `00033` не нужна. Если дубль всё же найдётся, создание индекса
   упадёт и миграция откатится без потери данных.
3. **Геймификация.** Фиксированные очки за публикацию обзора; `blockCount`
   убирается из события `review.published`; метрика `blocks_written` перестаёт
   расти, достижения на ней становятся недостижимыми.
4. **Переключение клиентов.** Одновременный релиз сервера и Mini App без
   версионирования API. Старые запросы с `blocks` отклоняются. Откат возможен
   только исправлением вперёд.

## Не проверено

- `internal/application/query/reviews.go` не прочитан: в SQL `read.Get` фильтра
  по статусу нет; закрыт ли черновик от посторонних выше по стеку — неизвестно.
- Общий лимит — 60 запросов в минуту (`RATE_LIMIT_PER_MIN`). Ключ лимита
  и `Retry-After` не изучены; автосохранение раз в секунду может в него
  упереться, на клиенте вероятно нужен минимальный интервал около 3 секунд.
- Подписчики `EventPublished` искались grep'ом с обрезкой вывода; найдена
  только геймификация.
