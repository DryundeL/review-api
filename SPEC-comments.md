# Spec: комментарии к отзывам

## Цель и допущения

Добавить в API комментарии к отзывам и ответы на комментарии произвольной
глубины. Фронтенд находится в другом репозитории: здесь реализуется контракт
для ленивой загрузки. Комментировать могут только авторизованные пользователи,
только опубликованные отзывы. Чтение комментариев также доступно только для
опубликованных отзывов. Черновики не раскрывают обсуждение.

## Контракт API

- `POST /v1/reviews/:id/comments`: JSON `{ "body": "Текст", "parentId": null }`.
  Для ответа `parentId` содержит UUID существующего комментария того же отзыва.
  Автор определяется сервером из текущей авторизации. Успех — `201`.
- `GET /v1/reviews/:id/comments?limit=20&cursor=...`: только корневые комментарии.
- `GET /v1/reviews/:id/comments?parentId=<uuid>&limit=20&cursor=...`:
  только непосредственные ответы выбранного комментария.
- Ответ списка: `{ "items": [], "nextCursor": null }`. Комментарий содержит
  `id`, `reviewId`, `parentId`, `author` (публичные данные автора), `body`,
  `createdAt`, `hasReplies`. Вложенные массивы автоматически не загружаются.
- Порядок: `created_at ASC, id ASC`; keyset-пагинация по этой паре без OFFSET.
  По умолчанию 20, допустимый limit — 1–50. Для определения следующей страницы
  выбирается не более `limit + 1` строк.
- Курсор непрозрачный для клиента, ограничен по длине, валидируется и привязан
  к отзыву и родителю. Некорректные UUID, limit и cursor отклоняются.
- Несуществующий/неопубликованный отзыв или родитель из другого отзыва — `404`;
  отсутствие авторизации при создании — `401`; некорректные поля — `422`
  (невалидный JSON — `400`).

## Валидация и хранение

- Текст: корректный UTF-8, после удаления внешних пробелов 1–2000 символов.
  Это обычный текст, без HTML-интерпретации; клиент выводит его как текст.
  Размер HTTP-тела ограничивается до разбора JSON.
- Новая Goose-миграция: `review_comments` с UUID, ссылками на отзыв и автора,
  nullable `parent_id`, текстом и серверным временем создания.
- Составной внешний ключ `(review_id, parent_id)` гарантирует принадлежность
  родителя тому же отзыву. Родитель неизменяем: создание циклов невозможно.
- Индекс `(review_id, parent_id, created_at, id)` обслуживает страницы и
  проверку наличия ответов. Не выполняется рекурсивное чтение дерева или
  подсчёт всех потомков. `hasReplies` вычисляется индексным EXISTS в запросе
  страницы без отдельного запроса для каждого комментария.
- Удаление отзыва удаляет его комментарии. Создание комментария и проверка
  опубликованности согласуются транзакционно с удалением/скрытием отзыва.
- SQL параметризован; внутренние ошибки БД не раскрываются клиенту.

## Структура и стиль

Существующий модуль `reviews`, слои `domain`, `application/command`,
`application/query`, `application/ports`, `infrastructure/write`,
`infrastructure/read`, `delivery/http`. Зависимости подключаются в `module.go`.
Создание проходит через доменную модель и транзакцию с outbox-событием,
как предписано `.cursor/rules/architecture.mdc`. Чтение возвращает DTO.
Новые библиотеки не требуются.

## Уведомления о комментариях


- Событие создания комментария записывается в outbox в одной транзакции
  с комментарием. Consumer подключается в worker через публичный контракт
  `reviews`, без импорта внутренних пакетов другого модуля.
- Повторная обработка события не дублирует inbox и не вызывает повторную
  отправку Telegram: стабильный ID уведомления зависит от комментария,
  получателя и типа. Сохраняется существующая семантика Telegram:
  доставка best effort, ошибка отправки не отменяет запись inbox.
- Inbox возвращает `reviewId`, `commentId` и `parentCommentId` (nullable),
  чтобы клиент мог открыть нужную ветку. Текст содержит автора действия и
  название отзыва; полный текст комментария в Telegram не передаётся.
- Если к моменту обработки отзыв удалён или снят с публикации,
  уведомление не создаётся и событие завершается без бесконечных повторов.
- Миграция расширяет каталог типов, пользовательские настройки и inbox;
  текущие настройки и существующие уведомления сохраняются.

Пример стиля:

```go
if parentID != nil && *parentID == uuid.Nil {
    return contract.FieldError{Field: "parentId"}
}
```

## Проверки и команды

- Unit: пустой/слишком длинный текст, Unicode, некорректные параметры и курсоры.
- Application/HTTP: авторизация, недоступный отзыв, чужой родитель, контракт
  ответа, пустая страница, отсутствие автоматической загрузки потомков.
- PostgreSQL: корни и ответы нескольких уровней, границы страниц при одинаковом
  времени, отсутствие дублей, ограничения FK, удаление отзыва, миграция up/down.
- Уведомления: правильный получатель для корня и ответа любой глубины,
  отсутствие уведомлений самому себе и всем предкам, повтор события,
  отключённый тип, отключённый Telegram, сбой Telegram, удалённый/скрытый отзыв,
  обратная совместимость настроек и поля навигации в inbox.
- `go test ./...`
- `go vet ./...`
- `go build ./cmd/...`
- Интеграционные тесты используют `TEST_DATABASE_URL` по существующему шаблону;
  отсутствие доступной тестовой БД явно указывается в результате проверки.

## Границы и критерии готовности

- Всегда: соблюдать текущую авторизацию и слои, проверять входные данные,
  ограничивать объём ответа, обновить документацию API для фронтенда.
- Требуют отдельного согласования: новые зависимости, изменение существующих
  прав доступа к отзывам, изменения API за пределами комментариев.
- Никогда: возвращать полное дерево, доверять переданному автору, раскрывать
  секреты, менять чужие незакоммиченные изменения.
- Готово: пользователь может создать корневой комментарий и ответ на любом
  уровне; клиент независимо листает каждый уровень; автор отзыва получает
  уведомление о корневом комментарии, автор комментария — о прямом ответе;
  настройки уведомлений соблюдаются; проверки проходят.
- В эту задачу не входят редактирование, удаление отдельных комментариев,
  реакции и жалобы.
