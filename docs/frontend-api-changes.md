# Изменения API для фронтенда

Документ описывает изменения страницы произведения, авторизации, приватности профиля, подписок и уведомлений. Контракты сверены с текущей реализацией backend.

Все пути ниже начинаются с `/v1`. Идентификаторы — UUID. Для защищённых запросов используется `Authorization: Bearer <jwt>`. Тела запросов и ответы — JSON, кроме CSV-импорта и ответов 204 без тела.

## 1. Что нужно изменить в существующем фронтенде

1. Читать жанр, год и статус произведения из `mediaObject.info`: прежние поля верхнего уровня убраны из ответов каталога и импорта.
2. Обрабатывать JSON-ответ `PUT /follows/:userId`: теперь успешный ответ имеет статус 200 или 202 вместо прежнего 204.
3. Для кнопки подписки использовать три состояния: `none`, `pending`, `following`. Значение `isFollowing=false` само по себе больше не означает отсутствие отправленного запроса.
4. Разрешить гостям открывать опубликованные обзоры и публичные разделы. Личные данные и операции изменения требуют входа.
5. Добавить переключатель `isProfilePrivate` в настройки пользователя и экран входящих запросов на подписку.
6. Добавить тип уведомления `follow_request`, его отображение и переключатель в настройках уведомлений.

## 2. Страница произведения

### Общая информация

`GET /media-objects/:id` — существующий эндпоинт с изменённым ответом. Авторизация не требуется.

Пример ответа 200:

```json
{
  "id": "11111111-1111-4111-8111-111111111111",
  "title": "Матрица",
  "originalTitle": "The Matrix",
  "type": "movie",
  "info": {
    "genre": "sci-fi",
    "releaseYear": 1999,
    "releaseStatus": "completed"
  },
  "posterUrl": "https://cdn.example.com/matrix.jpg"
}
```

`info` всегда присутствует и является объектом:

- `genre` — необязательная строка, до 100 символов.
- `releaseYear` — необязательное целое число от 1800 до 2100.
- `releaseStatus` — обязательная строка: `announced`, `ongoing`, `completed`, `hiatus`.

`originalTitle`, `posterUrl`, `externalSource`, `externalId`, `createdBy` могут отсутствовать. Для отсутствующих жанра, года и постера нужен соответствующий вариант отображения без данных.

Такой же формат объекта используется в `GET /media-objects?q=&type=&limit=` и в ответе импорта. Поля `genre`, `releaseYear`, `releaseStatus` на верхнем уровне больше не возвращаются.

Компактный `mediaObject`, вложенный в обзор, сохраняет прежний формат (`id`, `title`, `type`, `posterUrl`) и не содержит `info`. За метаданными произведения нужно обращаться к каталогу.

Неизвестный или некорректный ID произведения возвращает 404.

### Пять популярных обзоров

Новый эндпоинт: `GET /media-objects/:id/top-reviews`.

Авторизация необязательна. Возвращает до пяти опубликованных обзоров по количеству лайков, от большего к меньшему. При равенстве выше стоит более новый обзор; окончательный порядок определяется ID.

Пример ответа 200:

```json
{
  "items": [
    {
      "id": "22222222-2222-4222-8222-222222222222",
      "authorId": "33333333-3333-4333-8333-333333333333",
      "author": {
        "id": "33333333-3333-4333-8333-333333333333",
        "username": "reviewer",
        "isFollowing": false
      },
      "mediaObject": {
        "id": "11111111-1111-4111-8111-111111111111",
        "title": "Матрица",
        "type": "movie"
      },
      "title": "Почему фильм стоит посмотреть",
      "rating": 9,
      "status": "published",
      "hasSpoilers": false,
      "likesCount": 12,
      "dislikesCount": 1,
      "viewsCount": 120
    }
  ]
}
```

- Если обзоров нет: 200 и `{"items":[]}`. Если произведения нет: 404.
- Параметры `limit`, `offset` и страницы не применяются: размер выборки фиксирован.
- Полного текста и `blocks` в списке нет. Для открытия обзора: `GET /reviews/:id`.
- При передаче Bearer может присутствовать `viewerIsLike`: `true` — лайк, `false` — дизлайк. Если пользователь не голосовал или запрос гостевой, поле отсутствует.
- Не рассчитывать на наличие `followStatus` внутри `author`: новый статус подписки добавлен к ответам профиля и отдельного эндпоинта статуса.

Данные произведения и топ обзоров загружаются двумя независимыми запросами; единого ответа со всей страницей нет.

## 3. Авторизация и гостевой просмотр

`GET /reviews/:id` теперь доступен гостям для опубликованных обзоров. Черновик доступен только автору с Bearer; для остальных возвращается 404.

Без входа также доступны каталог, общий список обзоров, общая лента, поиск, публичный профиль и его публичные разделы. У большинства этих маршрутов гостевой режим уже существовал. Для получения персонального состояния передавать Bearer там, где авторизация необязательна: например, для голоса на обзоре или отношения к профилю.

На маршрутах с необязательной авторизацией переданный токен проверяется: некорректный или просроченный токен возвращает 401. Для гостевого запроса нужно убрать заголовок `Authorization`. Маршруты каталога `/media-objects` и `/media-objects/:id` не используют Bearer для персонализации.

Вход по-прежнему нужен для:

- создания, изменения и удаления обзора;
- лайка/дизлайка, регистрации просмотра через `PUT /reviews/:id/view`, жалобы;
- подписки, отмены подписки и работы с запросами на подписку;
- `/profile`, `/profile/reviews`, настроек, email и уведомлений;
- персональной ленты `/feed?mode=following`, покупок и личной геймификации.

Административные эндпоинты сохраняют защиту `X-Admin-Token`.

## 4. Приватность профиля

В `GET /settings` добавлено поле `isProfilePrivate`:

```json
{
  "isProfilePrivate": false,
  "language": "ru",
  "allowNotifications": true
}
```

Изменение: `PATCH /settings` с Bearer.

```json
{
  "isProfilePrivate": true
}
```

Ответ 200 содержит настройки целиком. PATCH частичный: остальные настройки можно не передавать. По умолчанию профиль публичный.

В ответах `GET /profile` и `GET /profiles/:id` добавлены `isProfilePrivate` и `followStatus`. Пример фрагмента:

```json
{
  "isProfilePrivate": true,
  "followStatus": "following",
  "isFollowing": true,
  "isMe": false
}
```

Страница приватного профиля и перечисленные разделы доступны владельцу и одобренным подписчикам:

- `GET /profiles/:id`;
- `GET /profiles/:id/reviews`;
- `GET /profiles/:id/following`;
- `GET /profiles/:id/followers`;
- `GET /profiles/:id/achievements`.

Остальным возвращается 404 без содержимого профиля. По одному такому ответу нельзя отличить закрытый профиль от несуществующего. Для отображения кнопки подписки можно отдельно запросить `/profiles/:id/follow-status`: для существующего закрытого профиля этот маршрут доступен.

Особенности:

- `pending` не даёт доступа к приватному профилю.
- Существующие подписчики сохраняют доступ при включении приватности.
- После удаления подписки доступ к закрытым разделам теряется.
- Опубликованные обзоры приватного автора остаются в общих лентах и доступны напрямую.
- Email, Telegram ID и другие личные поля профиля выдаются только владельцу, даже если подписка одобрена.
- Ответы профиля и его защищённых разделов имеют `Cache-Control: no-store`. После изменения приватности, подписки или текущего аккаунта нужно сбрасывать соответствующее состояние фронтенда.

## 5. Подписки и запросы

### Получение состояния

`GET /profiles/:id/follow-status` — доступен без обязательной авторизации, в том числе при закрытом профиле.

Пример ответа 200 для отправленного запроса:

```json
{
  "followStatus": "pending",
  "isFollowing": false
}
```

Состояния кнопки:

- `none` — «Подписаться».
- `pending` — «Запрос отправлен», доступно действие отмены.
- `following` — «Вы подписаны», доступно действие отписки.

`isFollowing` равно `true` только для `following`. Гостевой запрос возвращает `none`, поскольку пользователь не определён. Для собственного профиля кнопку подписки не показывать; подписка на себя запрещена.

Неизвестный или некорректный ID — 404. Этот маршрут возвращает только отношение к профилю, а не его содержимое или настройку приватности.

### Подписаться / отправить запрос

`PUT /follows/:userId` с Bearer, без обязательного тела.

- Для публичного профиля: 200 и `{"followStatus":"following","isFollowing":true}`.
- Для приватного профиля: 202 и `{"followStatus":"pending","isFollowing":false}`.
- Для уже существующей подписки или ожидающего запроса: 409 `CONFLICT`.
- Для несуществующего целевого пользователя: 404.
- Подписка на себя или некорректный ID: 422 `VALIDATION_ERROR`.

Успех этого эндпоинта больше не возвращает 204. После 200/202 нужно разобрать JSON и обновить кнопку по `followStatus`. При 409 запросить фактическое состояние, например после повторного клика или изменения из другой вкладки.

Альтернативный новый эндпоинт: `POST /profiles/:id/follow-requests`. Он использует тот же механизм и те же ответы: приватному профилю отправляет запрос, публичному создаёт подписку сразу. Не нужно вызывать оба эндпоинта для одного действия.

### Отменить запрос / отписаться

`DELETE /follows/:userId` с Bearer.

Удаляет либо ожидающий запрос, либо существующую подписку. Успех — 204 без тела, новое состояние — `none`. Если отношения уже нет — 404; фронтенд может сверить статус и обновить кнопку.

### Входящие запросы владельцу

`GET /profile/follow-requests?limit=20&offset=0` с Bearer.

Пример ответа 200:

```json
{
  "items": [
    {
      "userId": "33333333-3333-4333-8333-333333333333",
      "username": "reviewer",
      "isFollowing": false,
      "createdAt": "2026-10-25T14:00:00Z"
    }
  ]
}
```

`userId` — ID отправителя запроса. Может присутствовать `photoUrl`. Все элементы этого списка — ожидающие запросы; поле `isFollowing` не является статусом принятия запроса. Пустой список — `{"items":[]}`. Общее количество и поле следующей страницы не возвращаются.

По умолчанию `limit=20`, допустимо 1–50. В текущей реализации значение больше 50 заменяется на 20. `offset` — 0–10000. Некорректные параметры возвращают 422. Сортировка: сначала новые запросы, при равенстве даты — по ID отправителя.

### Принять / отклонить

Только владелец выполняет действия со своими входящими запросами:

- `PUT /profile/follow-requests/:userId` — принять.
- `DELETE /profile/follow-requests/:userId` — отклонить.

Здесь `userId` — ID отправителя. Тело не требуется. Успех — 204 без тела. Запрос исчезает из входящего списка. При принятии создаётся подписка и подписчик получает доступ к приватному профилю. При отклонении состояние отправителя становится `none`.

Если запрос отменён, уже обработан или не адресован текущему пользователю, возвращается 404. Нужно обновить входящий список; отсутствие запроса не следует считать новой ошибкой интерфейса. При некорректном ID — 422.

Ожидающие запросы не увеличивают счётчики подписчиков и не добавляют автора в ленту подписок. После принятия обновить входящий список и счётчики профиля. Отправитель узнаёт новое состояние через повторный запрос статуса: отдельного push-контракта для изменения кнопки нет.

Если владелец сделал профиль публичным, ожидающие запросы автоматически не принимаются. Отправитель может повторить действие подписки, либо владелец принять запрос из списка.

## 6. Уведомление о запросе

Добавлен тип `follow_request`. Уведомление получает владелец профиля при создании нового запроса. Оно поступает асинхронно через worker, поэтому может появиться после ответа 202.

Пример элемента в `GET /notifications?limit=20&offset=0`:

```json
{
  "id": "44444444-4444-4444-8444-444444444444",
  "type": "follow_request",
  "title": "Запрос на подписку",
  "body": "Новый запрос на подписку: @reviewer",
  "actorId": "33333333-3333-4333-8333-333333333333",
  "isRead": false,
  "createdAt": "2026-10-25T14:00:00Z"
}
```

Общий ответ списка сохраняет формат `{"items":[...]}`. Поля `reviewId` для этого типа нет. Если у отправителя нет username, текст может содержать его имя.

Для действий «Принять» / «Отклонить» использовать `actorId`, а не `id` уведомления. Уведомление является исторической записью: запрос к моменту клика мог быть отменён или уже обработан. Наличие актуального запроса проверяется через входящий список либо ответ действия.

Прочтение уведомления и обработка подписки — разные операции. Существующие маршруты сохраняются:

- `GET /notifications/unread` — счётчик непрочитанных: `{"count":1}`.
- `PATCH /notifications/:id/read` — отметить конкретное уведомление прочитанным.
- `PATCH /notifications/read` — отметить все прочитанными.

Все маршруты уведомлений требуют Bearer. Повторная отправка того же ожидающего запроса не создаёт новое уведомление; повторная обработка одного события также не создаёт дублей.

### Настройки уведомления

`GET /notification-settings` возвращает новый элемент в `items`:

```json
{
  "name": "follow_request",
  "title": "Запрос на подписку",
  "text": "Новый запрос на подписку",
  "enabled": true
}
```

Не привязывать интерфейс настроек к фиксированным двум типам `like` и `follow`: теперь есть третий тип `follow_request`.

Отключение через `PATCH /notification-settings`:

```json
{
  "items": [
    {
      "name": "follow_request",
      "enabled": false
    }
  ]
}
```

Ответ 200 возвращает весь список настроек. Отсутствующие в PATCH типы не изменяются.

- `follow_request.enabled=false` — отключены уведомления о запросах и в приложении, и в Telegram. Входящие запросы при этом остаются доступны.
- `allowNotifications=false` в `/settings` — выключена только отправка в Telegram; уведомления включённых типов в приложении сохраняются.

## 7. Изменения импорта для административного интерфейса

`POST /admin/media-objects/import` по-прежнему требует `X-Admin-Token`.

Новый JSON-формат:

```json
{
  "items": [
    {
      "title": "Матрица",
      "originalTitle": "The Matrix",
      "type": "movie",
      "info": {
        "genre": "sci-fi",
        "releaseYear": 1999,
        "releaseStatus": "completed"
      },
      "posterUrl": "https://cdn.example.com/matrix.jpg"
    }
  ]
}
```

Ответ — 201, `{"items":[...],"count":1}`. Метаданные элементов ответа находятся внутри `info`.

Для CSV используется заголовок `title,original_title,type,info,poster_url,external_source,external_id`; обязательны `title`, `type`, `info`. Пример корректного файла:

```csv
title,type,info
Матрица,movie,"{""genre"":""sci-fi"",""releaseYear"":1999,""releaseStatus"":""completed""}"
```

Прежний входной формат с отдельными метаданными пока принимается: JSON `genre`, `releaseYear`, `releaseStatus`; CSV `genre`, `release_year`, `release_status`. Не смешивать `info` с непустыми прежними полями в одной записи — это ошибка 422. Новый фронтенд должен отправлять вложенный формат.

## 8. Ошибки и обновление состояния

Общий формат ошибки:

```json
{
  "error": {
    "code": "NOT_FOUND",
    "message": "user not found"
  }
}
```

При ошибках валидации может присутствовать `error.details.field` и, для импорта, `error.details.index`.

- 401 `UNAUTHORIZED` — нужен вход либо передан недействительный токен.
- 404 `NOT_FOUND` — ресурс отсутствует или недоступен текущему пользователю; для действий над запросом также означает, что он уже не существует.
- 409 `CONFLICT` — подписка или ожидающий запрос уже существуют.
- 422 `VALIDATION_ERROR` — некорректные данные; для импорта неподходящий JSON также может возвращать 400.
- 500 — операция не подтверждена; перед повтором действия перечитать состояние.

Ответы 204 не содержат JSON: не вызывать для них `response.json()`.

После входа, выхода или смены аккаунта сбрасывать персональные данные: голос на обзоре, статус подписки, доступ к профилю, входящие запросы и уведомления. После успешной мутации перечитывать затронутые списки и счётчики. Не сохранять сведения закрытого профиля в общем кэше, доступном другому пользователю.

## 9. Готовность backend

Перед включением нового фронтенда нужны API и worker с текущими изменениями и миграции:

- `00020_media_object_info.sql` — метаданные произведения в `info`.
- `00021_profile_privacy.sql` — настройка приватности.
- `00022_follow_requests.sql` — ожидающие запросы на подписку.
- `00023_follow_request_notifications.sql` — уведомления и их настройка.

Старый API несовместим со схемой после переноса колонок в `info`. Frontend-контракты каталога и ответа на подписку нужно обновлять согласованно с backend.
