# Frontend: выбор предпочтений контента

## Задача и границы

При загрузке приложения после авторизации проверить собственный профиль. Если
пользователь ещё не сохранял предпочтения, показать выбор любимых типов контента:
манга, манхва, книги, фильмы и другие типы из справочника backend.

Выбор сохраняется на сервере для текущего аккаунта и доступен после перезапуска,
повторного входа и на другом устройстве. В этой версии выбираются **типы контента**,
а не жанры и не конкретные произведения.

Backend предоставляет проверку необходимости опроса, справочник типов и
чтение/сохранение предпочтений. Эндпоинта `/v1/recommendations` нет. Сохранение
выбора само по себе не меняет выдачу существующих лент и каталога.

## 1. Что реализовать на frontend

1. Добавить `needsOnboarding: boolean` в модель собственного профиля.
2. После успешной загрузки `GET /v1/profile` проверять это поле.
3. При `true` открыть экран или модальное окно с множественным выбором типов.
4. Загрузить варианты из `GET /v1/review-types`.
5. Отправлять полный выбор через `PUT /v1/content-preferences`.
6. После успешного сохранения обновить локальное состояние профиля и закрыть опрос.
7. Предусмотреть изменение выбора в настройках: сначала прочитать сохранённые
   предпочтения через `GET /v1/content-preferences`.

Опрос относится к авторизованному пользователю. Для гостя его не запускать.
Проверка выполняется после загрузки собственного профиля, а не при просмотре
произвольного публичного профиля.

## 2. Проверка при запуске: собственный профиль

```http
GET /v1/profile
Authorization: Bearer <jwt>
```

Успех: `200 OK`. Фрагмент ответа — остальные поля профиля остаются прежними:

```json
{
  "id": "11111111-1111-4111-8111-111111111111",
  "firstName": "Анна",
  "isMe": true,
  "needsOnboarding": true
}
```

Смысл поля:

- `true` — у аккаунта нет сохранённого выбора; нужно показать опрос.
- `false` — выбор уже сохранён; автоматически показывать опрос не нужно.

У существующих пользователей без предпочтений тоже будет `true`: дата регистрации
не влияет на это поле. После успешного сохранения следующий запрос профиля вернёт
`false`. Обновление Telegram-профиля и повторный вход не сбрасывают выбор.

`needsOnboarding` присутствует в собственном профиле, включая обращение к
`GET /v1/profiles/:id` с ID своего аккаунта. В ответе для чужого профиля поля нет.
Поэтому в общей модели публичного профиля поле должно быть необязательным,
а в модели успешного ответа `/v1/profile` — обязательным.

Не нужен дополнительный `GET /content-preferences` только ради решения, показывать
ли опрос. Не считать отсутствие поля эквивалентом `true`: это может быть чужой
профиль или несовместимая версия backend.

## 3. Варианты выбора: справочник типов

```http
GET /v1/review-types
```

Авторизация не требуется. Успех: `200 OK`. Пример структуры; фактический список
может быть больше:

```json
{
  "items": [
    {"code": "manga", "imageUrl": "/storage/review-types/manga.webp", "label": "Манга", "sortOrder": 10},
    {"code": "manhwa", "imageUrl": "/storage/review-types/manhwa.webp", "label": "Манхва", "sortOrder": 20},
    {"code": "book", "imageUrl": "/storage/review-types/book.webp", "label": "Книга", "sortOrder": 60}
  ]
}
```

- Показывать пользователю `label`, хранить и отправлять `code`.
- Сохранять порядок сервера: backend сортирует по `sortOrder`, затем по `code`.
- Ответ уже содержит только активные типы. Поля `isActive` в публичном ответе нет;
  дополнительный фильтр `item.isActive` удалит все варианты.
- Не зашивать фиксированный список кодов в приложение.
- Справочник имеет `Cache-Control: public, max-age=60`.

Если список не загрузился, показать ошибку и кнопку повтора. Если `items` пуст,
показать, что варианты временно недоступны. В обоих случаях не отправлять пустой
выбор и не отмечать опрос завершённым.

## 4. Сохранение выбора

```http
PUT /v1/content-preferences
Authorization: Bearer <jwt>
Content-Type: application/json

{"types":["manga","manhwa","book"]}
```

Успех: `200 OK`, тело ответа:

```json
{
  "types": ["manga", "manhwa", "book"],
  "needsOnboarding": false
}
```

Это полная замена списка, а не добавление отдельных элементов. Например, после
`{"types":["manga","book"]}` запрос `{"types":["book"]}` оставит только `book`.
Backend берёт пользователя из токена; `userId`, `telegramId` и другие идентификаторы
в теле передавать не нужно. Лишние поля отклоняются.

Ограничения запроса:

- От 1 до 32 кодов включительно.
- Каждый код — строка из актуального справочника активных типов.
- Повторы запрещены; сравнение чувствительно к регистру.
- Формат кода: `^[a-z][a-z0-9_]{0,31}$`. Пробелы не обрезаются, регистр не исправляется.
- Тело JSON ограничено 4096 байтами.
- `types: []`, `types: null`, отсутствие `types`, неизвестные и неактивные коды
  не принимаются.

На клиенте удобно держать выбранные коды в `Set<string>`, а перед отправкой
преобразовывать в массив. Кнопка сохранения недоступна при пустом выборе и во время
запроса. Пока запрос выполняется, блокировать повторное сохранение и изменение
выбора либо явно отделять отправленный снимок от редактируемого черновика.

После `200`:

1. Взять сохранённые `types` и `needsOnboarding` из ответа.
2. Обновить кэш предпочтений текущего пользователя.
3. Обновить `needsOnboarding` в кэше собственного профиля на `false` либо
   инвалидировать профиль и перечитать его.
4. Закрыть опрос и продолжить обычный сценарий приложения.

Не закрывать опрос и не менять признак завершения до успешного ответа.
Запросы изменения выбора отправлять последовательно: при нескольких успешных
сохранениях, в том числе с разных устройств, действует последний записанный список.

## 5. Чтение и редактирование сохранённого выбора

```http
GET /v1/content-preferences
Authorization: Bearer <jwt>
```

Успех: `200 OK`. До первого сохранения:

```json
{"types":[],"needsOnboarding":true}
```

После сохранения:

```json
{"types":["manga","book"],"needsOnboarding":false}
```

Для экрана настроек загрузить предпочтения и справочник. Отметить выбранными коды
из `types`, разрешить изменить набор и сохранить его тем же PUT. Отмена
редактирования должна отбрасывать локальный черновик, не отправляя запрос.

Сохранённый код может исчезнуть из активного справочника, если администратор
деактивировал тип. Сервер не очищает прежний выбор автоматически и не возвращает
из-за этого `needsOnboarding: true`. Такой код нельзя повторно сохранить.
Показывать для него состояние «больше недоступен» либо исключить его из черновика
с пояснением пользователю; при следующем сохранении отправить только активные
коды. Если активных выбранных кодов не осталось, попросить выбрать хотя бы один.

Сброса выбора через DELETE или пустой PUT нет. Отдельного API для «пропустить»
тоже нет. Если интерфейс разрешает закрыть первоначальный опрос без сохранения,
это только локальное действие: сервер продолжит возвращать `needsOnboarding: true`
при следующей загрузке профиля.

## 6. Ошибки и восстановление

Ошибки имеют общий формат API. Для некорректного набора типов:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "invalid settings",
    "details": {"field": "types"}
  }
}
```

Обрабатывать по HTTP-статусу и `error.code`, а не по тексту `message`.

- **400 / `VALIDATION_ERROR`**: некорректный JSON, неверный тип поля, лишнее поле,
  несколько JSON-значений или превышение лимита тела. Сохранить черновик и показать
  ошибку. Не повторять тот же некорректный запрос автоматически.
- **401 / `UNAUTHORIZED`**: использовать общий сценарий восстановления авторизации.
  Не сохранять выбор от имени другого аккаунта после смены пользователя.
- **422 / `VALIDATION_ERROR`, `details.field = "types"`**: проверить ограничения
  списка и обновить справочник. Тип мог стать неактивным между загрузкой и PUT.
  Сохранить допустимые выбранные коды, показать проблему и дать исправить выбор.
- **404 / `NOT_FOUND`**: профиль или связанный ресурс недоступен. Не считать опрос
  завершённым; проверить сессию и повторно загрузить собственный профиль.
- **429**: применяется общий лимит API. Остановить частые повторы и дать повторить
  позже в соответствии с общим обработчиком приложения.
- **5xx, таймаут, обрыв сети**: результат PUT может быть неизвестен. Не отмечать
  локально успех; после восстановления связи перечитать `/content-preferences`.
  При необходимости пользователь может повторить PUT с тем же полным списком —
  дубликаты предпочтений не создаются.

Если загрузка `/profile` завершилась ошибкой, состояние опроса неизвестно. Показать
состояние ошибки/повтора, а не подставлять `needsOnboarding: false`.

## 7. Состояние клиента и приватность

Рекомендуемые состояния формы: загрузка, выбор, сохранение, ошибка. Ошибка
сохранения не должна стирать черновик. Предпочтения не требуется сохранять при
каждом нажатии на вариант: отправлять один PUT по кнопке подтверждения.

`/profile` и `/content-preferences` возвращают `Cache-Control: no-store`.
Не помещать ответы в общий публичный кэш. Внутренний кэш приложения привязывать
к аккаунту; при выходе или смене аккаунта очищать профиль, предпочтения, черновик
и состояние опроса. Отменять устаревшие запросы или игнорировать их ответы, если
пользователь уже сменился. Не хранить токен в логах, URL или сообщениях ошибок.

## 8. Критерии приёмки frontend

- Новый пользователь и существующий пользователь без выбора видят опрос после
  загрузки собственного профиля с `needsOnboarding: true`.
- Пользователь с сохранённым выбором не видит опрос автоматически.
- Гость и посетитель чужого профиля не получают опрос по данным чужого профиля.
- Варианты приходят из `/review-types`; несколько вариантов можно выбрать и снять.
- Без выбора сохранение недоступно; двойное нажатие не отправляет параллельные PUT.
- После успешного PUT окно закрывается, состояние профиля обновляется.
- После перезапуска и повторного входа выбор сохраняется, опрос не появляется.
- В настройках отображается прежний выбор; изменение заменяет весь список.
- Ошибка сети сохраняет черновик и позволяет восстановить актуальное состояние.
- Устаревший/неактивный тип обрабатывается без потери остальных допустимых кодов.
- Выход и смена аккаунта не переносят выбор или поздние ответы между аккаунтами.
- Клиент не обращается к `/recommendations`.

## 9. Готовность backend

До подключения frontend развернуть backend с этими изменениями и применить
миграцию `00028_content_preferences.sql` вместе с предшествующими миграциями.
Проверить на целевой среде полный сценарий: профиль до выбора → PUT → профиль
после выбора → повторный вход → чтение предпочтений.
